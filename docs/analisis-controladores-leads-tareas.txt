Analisis de LeadController y TareaController
Generado: 09/05/2026

Este documento analiza los casos de uso, responsabilidades, entradas, salidas,
rutas MVC, validaciones, uso de sesion, patron PRG, self::view(), arrays,
bucles y respuestas JSON de:

- app/controllers/LeadController.php
- app/controllers/TareaController.php

Nota de nombre: el archivo real del proyecto es TareaController.php, aunque en
la peticion se mencione TareasController.


1. FLUJO MVC GENERAL
====================

1. El navegador solicita una ruta.
2. public/index.php carga routes/web.php.
3. routes/web.php registra rutas GET y POST con Route::get() y Route::post().
4. Route::handleRoute() lee $_SERVER['REQUEST_URI'] y $_SERVER['REQUEST_METHOD'].
5. Si la ruta es estatica, llama directamente al controlador con call_user_func().
6. Si la ruta tiene parametros, por ejemplo /leads/{id}, extrae el parametro y
   llama al controlador con call_user_func_array($handler, $params).
7. El controlador inicia sesion, valida permisos, lee GET/POST o parametros de
   la firma, llama al modelo y decide una salida.
8. La salida puede ser:
   - self::view(...): renderiza una vista PHP.
   - header('Location: ...') + exit(): redireccion PRG.
   - echo json_encode(...): respuesta JSON para JavaScript/fetch.


2. USO DE SESION EN ESTOS CONTROLADORES
=======================================

Cuando se inicia sesion:
- Casi todos los metodos llaman a SessionManager::iniciarSesion().
- Los metodos privados no inician sesion directamente, porque se ejecutan desde
  metodos publicos que ya la han iniciado.

Por que se usa sesion:
- Para comprobar autenticacion con SessionManager::usuarioNoAutenticado().
- Para leer el usuario actual con SessionManager::get('usuario').
- Para saber id y rol del usuario: id, rol.
- Para guardar mensajes flash antes de redirigir.

Cuando guarda en sesion:
- Usa SessionManager::setMensajeFlash($mensaje, $icono, $clase).
- Esto se usa antes de un header('Location: ...') para que la siguiente vista
  pueda mostrar el resultado de la operacion.
- Es necesario porque una redireccion corta la request actual y empieza otra.

Variables que no se recomiendan en sesion:
- Formularios completos con datos sensibles.
- Passwords, tokens largos, datos bancarios o datos privados de leads.
- Listados grandes de leads/tareas.
- Resultados completos de consultas SQL.
- Objetos de modelo o conexion.
- Datos que deben estar siempre actualizados en base de datos, como estado,
  prioridad o valor de un lead.

Uso correcto en este proyecto:
- Guardar solo usuario autenticado y mensajes flash cortos.
- Reconsultar datos reales desde modelo cuando se renderiza una vista.


3. PATRON PRG Y SELF::VIEW
==========================

PRG significa Post/Redirect/Get.

Cuando se usa PRG:
- Despues de una operacion POST correcta.
- Despues de un error de persistencia que conviene mostrar en otra carga.
- Para evitar que el navegador repita el POST al refrescar.

Ejemplos:
- nuevoContacto() guarda lead publico y redirige a /contacto.
- nuevoLead() guarda lead interno y redirige a /panel.
- cambiarEstado() actualiza estado y redirige a /panel o /leads/{id}.
- nuevaNota() guarda actividad y redirige a /leads/{id}.
- eliminarLead() elimina y redirige a /panel.
- guardar(), actualizar() y eliminar() de TareaController redirigen a /tareas.

Cuando se usa self::view():
- En rutas GET que solo muestran pantalla.
- En POST con errores de validacion, para devolver la misma vista con errores y
  valores escritos por el usuario sin hacer redireccion.

Ejemplos:
- mostrarFormContacto(), mostrarFormLead(), mostrarDetalle(), mostrarListado().
- nuevoContacto() si hay errores de formulario.
- nuevoLead() si hay errores de formulario.
- actualizarLead() si hay errores de edicion.
- TareaController::renderIndex() para la vista principal de tareas.
- guardar() y actualizar() de tareas usan renderIndex() si hay errores.


4. METODOS DE ARRAY, BUCLES Y ORGANIZACION DE DATOS
===================================================

Arrays asociativos:
- Se usan para errores: $errores['campo'] = 'mensaje'.
- Se usan para datos de formularios: $leadForm, $datosForm, $datosEdicion.
- Se usan para pasar datos a vistas con self::view().
- Se usan para pasar datos a modelos create(), update(), createHistorial().

empty():
- Comprueba si hay errores: if (!empty($errores)).
- Comprueba nuevas tareas asignadas: if (!empty($nuevasAsignadas)).
- Decide si se crea historial de campos modificados.

in_array(..., ..., true):
- Valida que estados, prioridades, servicios, origenes, tipos de actividad,
  tipos de bloqueo y soluciones pertenezcan a listas permitidas.
- El tercer parametro true fuerza comparacion estricta.

array_map():
- En nuevoLead() y actualizarLead() convierte la lista de responsables en lista
  de ids:
  $idsResponsables = array_map(static fn($r) => (int) $r['id'], $responsables);
- Resultado: permite validar responsable_id con in_array().

is_array():
- En mostrarListado() asegura que usuario, filtros y listas lleguen a la vista
  como arrays aunque el modelo devuelva algo inesperado.

implode():
- En actualizarLead() convierte campos modificados en una frase:
  implode(', ', $camposModificados).

foreach:
- En actualizarLead() recorre $mapaComparacion.
- Compara valores anteriores y nuevos.
- Resultado: genera $camposModificados para registrar historial legible.

Desestructuracion de arrays:
- En mostrarListado(), si fecha_desde es mayor que fecha_hasta, intercambia:
  [$filtros['fecha_desde'], $filtros['fecha_hasta']] =
  [$filtros['fecha_hasta'], $filtros['fecha_desde']];

Switch:
- En TareaController::getTextoInfoSolucion() decide el texto segun la solucion
  elegida para una objecion.


5. ECHO JSON_ENCODE: CUANDO SE USA Y POR QUE
============================================

Solo aparece en LeadController::cambiarEstadoKanban().

Ruta:
- POST /pipeline/cambiar-estado

Origen:
- public/js/kanban.js usa fetch() cuando el usuario arrastra una tarjeta del
  Kanban a otra columna.

Por que usa echo json_encode:
- Porque no es una navegacion normal ni un formulario tradicional.
- Es una peticion asincrona desde JavaScript.
- El navegador no necesita una pagina HTML nueva.
- JavaScript necesita una respuesta estructurada para saber si mantiene el
  movimiento de la tarjeta o si debe revertirlo.

Flujo MVC JSON:
1. La vista Kanban renderiza tarjetas con data-id y data-estado.
2. kanban.js detecta el drop de la tarjeta.
3. kanban.js envia fetch POST a /pipeline/cambiar-estado.
4. Route::handleRoute() detecta POST /pipeline/cambiar-estado.
5. Route llama a LeadController::cambiarEstadoKanban().
6. El controlador inicia sesion.
7. Establece header('Content-Type: application/json; charset=utf-8').
8. Valida usuario, lead_id y estado.
9. Llama a LeadModel para buscar y actualizar el lead.
10. Crea historial y acciones automaticas si procede.
11. Devuelve JSON con echo json_encode(...).
12. kanban.js interpreta la respuesta.

Respuestas JSON posibles:
- Sin sesion:
  http_response_code(401)
  {"ok": false, "mensaje": "Debes iniciar sesion."}

- Datos invalidos:
  http_response_code(422)
  {"ok": false, "mensaje": "Los datos enviados no son validos."}

- Lead inexistente:
  http_response_code(404)
  {"ok": false, "mensaje": "No se ha encontrado el lead."}

- Error al actualizar:
  http_response_code(500)
  {"ok": false, "mensaje": "No se ha podido actualizar el estado."}

- Estado repetido:
  {"ok": true, "mensaje": "El lead ya estaba en ese estado.",
   "estadoAnterior": "...", "estadoNuevo": "..."}

- Exito:
  {"ok": true, "mensaje": "...", "estadoAnterior": "...",
   "estadoNuevo": "...", "leadId": 123}

Diferencia con self::view():
- self::view() entrega HTML para una pantalla completa.
- echo json_encode() entrega datos para que JavaScript actualice la pantalla
  actual sin recargar.

Diferencia con PRG:
- PRG redirige despues de un POST de formulario.
- JSON no redirige; responde dentro de la misma peticion fetch.

----------------------------------------------------------

Caso de uso:
- Validar filtros GET de fecha en el listado de leads.

10.3 LeadController::cambiarEstadoKanban(): void
------------------------------------------------

Ruta:
- POST /pipeline/cambiar-estado

Caso de uso:
- Actualizar estado de un lead desde drag and drop del Kanban sin recargar.

Recibe:
- $_POST['lead_id']
- $_POST['estado']
- usuario desde sesion.

Devuelve:
- JSON con echo json_encode().

Validacion:
- Si no hay usuario en sesion, devuelve 401.
- lead_id debe ser > 0.
- estado debe estar en LeadModel::getEstados().
- lead debe existir.
- updateEstado() debe devolver true.

Logica:
- Declara Content-Type JSON.
- Valida sesion manualmente en vez de usar usuarioNoAutenticado(), porque una
  redireccion a login no serviria para fetch.
- Si falla, responde JSON y codigo HTTP.
- Si el estado es el mismo, responde ok sin actualizar.
- Actualiza estado.
- Crea historial.
- Si entra en Objeciones, crea tarea automatica.
- Si entra en Ganado, crea notificacion.
- Devuelve JSON para que kanban.js decida si mantiene o revierte la tarjeta.

Por que no usa PRG:
- Porque el cliente es fetch(), no un formulario HTML.
- No se debe redirigir; se deben entregar datos JSON.

Por que no usa self::view:
- No necesita HTML.
- La vista ya esta cargada en el navegador.
- JavaScript solo necesita estado de exito/error y mensaje.

Metodos de array:
- in_array() para validar estado.
- Arrays asociativos para json_encode().

12. CONCLUSION
==============

LeadController concentra los casos de uso del ciclo de vida del lead: entrada
publica, alta interna, cambio de estado, detalle, notas, edicion, borrado,
listado y actualizacion asincrona desde Kanban.

TareaController concentra los casos de uso de seguimiento: listado operativo,
creacion, edicion, borrado, permisos por usuario y apoyo especifico para
objeciones.

La regla general del proyecto es clara:
- GET renderiza vistas.
- POST de formulario valida, guarda flash y redirige con PRG.
- POST con fetch devuelve JSON con echo json_encode().
- self::view() se usa cuando hay que mostrar HTML en la misma request.
- La sesion se usa para autenticacion y flashes, no para almacenar datos de
  negocio completos.
